# Owner-created employee accounts

Staff & Permissions → Add Employee supports both invitations and creating a dedicated work account. Use an invitation when the person already has a Supabase Auth account at that address. Direct creation never assigns the owner role or attaches an existing customer account. The owner must be signed in with an active, email-verified owner account; supplying staff or customer credentials can't call the protected provisioning RPC.

## Release checklist

1. Review and release any unapplied POS authorization and Staff Management migrations first. Then apply `20261115170000_owner_created_employee_accounts.sql` to the intended Golden Rose project only.
2. Release the matching `pos-register` function and Next.js changes. POS must use the new session check, which rejects pre-rotation sessions even after the membership becomes active again. Ensure any other deployed staff APIs that need immediate revocation of existing JWTs check the same session guard with a verified `session_id`.
3. Configure `SUPABASE_STAFF_ADMIN_SECRET_KEY` using a dedicated server-only Supabase secret key (`sb_secret_…`). Never add a `NEXT_PUBLIC_` prefix or reuse the browser publishable key. Store it in the environment secret store. No secret is required to build the app or use invitations.
4. Keep email confirmation enabled in Supabase Auth, confirm that the signup confirmation email can be delivered (SMTP and template), and allow the site's `/staff/login` redirect URL. The Supabase CLI config currently disables email confirmation; enable it in a disposable local instance for mail tests. Direct account creation sets `email_confirm: false` and the database rejects a newly provisioned identity that arrives pre-confirmed. An SMTP request is not proof of email delivery.
5. Confirm the real store is active and loaded in Inventory. With designated test accounts in a disposable project, test creation, email confirmation, first password change and a fresh staff login. Check that an owner can operate POS under their own account, that the cashier sees only their assigned store, and that neither old JWTs nor suspended or revoked cashiers can transact.

## Operation and recovery

- The owner enters a strong temporary password twice and shares it privately. It expires for work access after 24 hours; it is never stored in app tables, emitted in an audit event or echoed in an action result.
- A new or reset employee starts without active staff access. Once their work email is confirmed, staff login routes them to the password change screen. The employee enters the current password and a different password. The database checks the confirmed work email and that the Auth password changed before activating the membership. A fresh sign-in is required after activation.
- An interrupted create can leave an Auth account without an employee membership. Repeat Add Employee with the same work email: a private reservation marker links only the account created by this flow. Recovery keeps the password from the original successful Auth request; use **Replace temporary password** if it is unknown. An unrelated account is never attached or deleted.
- Replacement is limited to dedicated work accounts created by this flow, so an owner cannot overwrite a customer's existing password if they joined through an invitation. Invited employees use existing email recovery. Replacements block business access before the Auth write. After an interrupted replacement, wait two minutes, then retry. An account suspended for staff reasons must be restored separately before a replacement is allowed. Revoked accounts cannot be reset.
- Audit records cover account creation, starting and completing replacement, and employee password changes. The local SQL test uses synthetic Auth rows and exercises the real membership, store and session checks. A disposable Auth server and its mailbox are required to verify delivery and the full browser sign-in flow.
